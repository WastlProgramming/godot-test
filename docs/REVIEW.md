## Findings (most severe first)

| ID | Sev | File:Line | Issue | Suggested fix |
|---|---|---|---|---|
| R-01 | High (plausible) | `scripts/World/WorldGenerator.cs:179-186`, `scripts/World/MovingPlatform.cs:17,29` | **Floating-origin shift vs. moving platforms.** `ShiftOrigin` moves each chunk's `Position` by about 1000 m. `MovingPlatform` is an `AnimatableBody3D` with `SyncToPhysics = true`, so the physics server treats the jump as kinematic motion and reports a one-frame linear velocity of about 60 000 m/s. If the player is standing on a moving platform when the shift happens, `CharacterBody3D` takes that as platform velocity (moved with it, or `platform_on_leave = ADD_VELOCITY`). The player is thrown about 1000 m, falls, and loses the run. | Run the shift only while the player stands on a static floor (`GetLastSlideCollision()?.GetCollider() is not MovingPlatform`) or is airborne. Or turn `SyncToPhysics` off on all `MovingPlatform`s for the shift frame and reset `_start`. Or shift with `PhysicsServer3D.BodySetState(rid, Transform, …)` and set velocity to zero. |
| R-02 | Medium | `scripts/Items/TrampolineItem.cs:22`, `scenes/objects/Trampoline.tscn` (BounceArea r = 1.15), `scripts/Items/Trampoline.cs:42` | **The trampoline fires as soon as it is placed.** It is placed 1.5 m in front of the player's center. The player capsule has radius 0.4 and the BounceArea radius 1.15, so they overlap by about 0.05 m. On the next physics step `BodyEntered` fires with `Velocity.Y ≈ 0 ≤ 1`, and the player is launched 10 m straight up where they stand, usually not next to the wall. The bounce is wasted. | Place it further away (≥ 1.15 + 0.4 + margin, e.g. 2.0 m), or shrink the BounceArea to the pad radius (~0.8). Also require the player to be above the pad (`p.GlobalPosition.Y > GlobalPosition.Y + 0.2f`) and/or ignore entries in the first ~0.2 s after placing. |
| R-03 | Medium | `scripts/World/ChunkBuilder.cs:252`, `scripts/Game/GameConstants.cs:34`, `scripts/Items/BridgeItem.cs:28` | **The bridge can be too short for the BigGap.** Gap = `Lerp(12,14,D) + U(0,2)`, so up to 16 m. `BridgeLength` is exactly 16 m and the bridge starts at the player's center. Standing a little back from the edge, or aiming the camera a few degrees off the path (reach = 16·cos θ), leaves the bridge short. The guarantee crate before a BigGap drops only a bridge (`ChunkBuilder.cs:118`), so the guaranteed solution can fail at high difficulty. | Cap the gap at `BridgeLength - 2` (e.g. `Mathf.Min(gap, GameConstants.BridgeLength - 2.5f)`), or make the bridge longer (20 m). Optionally snap the bridge start to the platform edge with a down-ray, and snap the yaw to the path direction (−Z) when it is within about 20°. |
| R-04 | Low | `scripts/Player/PlayerController.cs:224-228`, `scripts/Items/GrappleHook.cs:14-19` | **The grapple cannot be released with E after its last charge.** `UseSelectedItem` returns "Keine Ladung mehr" before `GrappleHook.TryUse` runs, so the "release" branch is never reached when the count is 0. When it is reached, the release is reported through `ItemUseFailed` ("Enterhaken gelöst") and shows up in the HUD as an error. | Handle `IsGrappling` in `UseSelectedItem` before the charge check (`if (IsGrappling) { StopGrapple(true); return; }`). Remove the release branch from `TryUse`. |
| R-05 | Low | `scripts/Items/Crate.cs:65` | `parent.CallDeferred(AddChild, p)`: if the parent chunk is despawned in the same frame, the deferred call targets a freed object and is dropped. The instantiated `Pickup` is then an orphan node (leak). | Add the child right away (`parent.AddChild(p)` is safe here because the crate is hit from `_PhysicsProcess`, not from a physics callback). Or use a lambda that frees `p` when the parent is invalid, as `SpawnEffect` already does. |
| R-06 | Low | `scripts/Game/GameManager.cs:49,76-80` | `_settingsDirty` is written but never read. The autosave only checks `_highscoreDirty`, so sensitivity and invert-Y changes are saved only on menu, restart, quit or window close. A crash loses them. | `if (_highscoreDirty \|\| _settingsDirty) SaveAll();`, or save settings when the pause menu closes. |

## Lifecycle and safety checklist

- Physics runs in `_PhysicsProcess`: player, world generator, moving platforms and lifetimes are correct. `_Process` is used only for camera follow, HUD and pickup bobbing. OK.
- `QueueFree` is used correctly: chunks are removed from the list before `QueueFree`, and `IsInstanceValid`/`IsQueuedForDeletion` guards are in place. OK. (Watch R-05.)
- Node paths: all lookups use `GetNodeOrNull` with fallbacks or warnings, `%UniqueName` nodes exist in the HUD, pause and main menu scenes, and `Main.tscn` matches `WorldRoot/Chunks|Placeables|WorldGenerator`. OK.
- Signals: C# `+=` on Godot signals is paired with `-=` in `_ExitTree` (see R-07 for robustness). The tween is killed before reuse. OK.
- Save system: fixed `user://` whitelist, 4 KB size limit, strict UTF-8, `JsonDocument` with `MaxDepth`, version check, value clamping, atomic write (tmp → rename). The seed input is digits only with a length limit. No security issues found.
